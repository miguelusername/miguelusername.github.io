Zombie Taxi — Zombie AI and Pathfinding

A hundred agents, each independently searching the entire scene for the player every frame and re-solving a full navigation path every frame. Restructured so per-frame cost is capped by a budget instead of by the population.

Browse original code Browse enhanced code Narrative (DOCX)

The artifact

Zombie Taxi is a Unity game I built with a team for GAM-360 earlier this year — an arcade driving game where you play a taxi driver in a zombie apocalypse, picking up and dropping off passengers in an overrun city, and running zombies over with the car. I owned the zombie systems: the spawner, the individual zombie behavior, the zombie variants and the anti-zombie zones.

The map spawns 100 zombies at once. Each wanders a NavMesh until the taxi gets close, then drops what it's doing and chases.

Three data structures

All three are plain C# in their own assembly with no MonoBehaviour dependency, which is what makes them unit-testable.

Uniform spatial hash grid

Buckets agents into fixed-size cells on the XZ plane, so a proximity query only visits the cells the search circle actually overlaps — O(c + k) rather than O(n), where c is overlapped cells and k is the agents inside them. With the cell size tuned near the query radius, c is a small constant and k tracks local crowding rather than total population.

Before — scan everything, with a square root each
foreach (GameObject z in allZombies)
{
    if (z != null)
        if (z.GetComponent<Zombie>().zombieHealth > 0)
            if (Vector3.Distance(transform.position,
                    z.transform.position) < closest)
            {
                Debug.Log("Tracker: Found Zombie");
                trackingTarget = z;
                closest = Vector3.Distance(transform.position,
                    z.transform.position);
            }
}
After — one indexed query
if (manager.TryFindNearestZombie(
        transform.position,
        maximumDistanceCheck,
        out Zombie nearest)
    && nearest != null && nearest.IsAlive)
{
    trackingTarget = nearest;
}

Round-robin update scheduler

Hands out a fixed-size slice of the population each tick and remembers where it stopped, so per-frame cost is bounded by the budget rather than by n. With 100 zombies and a budget of 25, every zombie is serviced once every four frames. The trade-off is up to four frames of decision latency — invisible on something that shambles, unacceptable for a projectile.

Distance-based level of detail

Agents are classified Near, Mid or Far by squared distance, so no square root is needed. The band decides how often an agent may re-solve a path, and Far agents skip the expensive work and the animation blending entirely.

The spawner

Spawn point selection used rejection sampling: up to 200 attempts per zombie, each costing two NavMesh.SamplePosition calls with a 200-unit search radius. Cost per zombie was unbounded and depended on how much of the bounding box happened to be road.

It now reads the NavMesh triangulation once, keeps the centroid of every road-tagged triangle in a list, and spawning is a single random index into it — O(m) once, then O(1) per zombie. Spawns are also spread across frames so a hundred instantiations don't land on one.

Measured result

I wrote a benchmark that runs the old linear scan and the new grid query over identical data, and asserts both return the same results before reporting any timing.

The rebuild cost is the honest half of that trade. The grid isn't free — it costs about 40 microseconds to rebuild — but it pays for itself after roughly four queries, and it's rebuilt five times a second rather than every frame.

The regression, and how I caught it

My first version added a quarter-second cooldown on top of the update budget. Every structural test passed. The zombies stopped attacking the player.

A taxi at 70 km/h travels about five metres in a quarter second, so every chasing zombie was steering at a point the car had already left, trailing it instead of making contact — and no contact means no collision, which means no damage. Nothing that tested a hash grid or a scheduler knew how fast a taxi drives.

The fix was to let close agents re-path every time they're serviced and let the budget do the throttling by itself, which is still a quarter of the original cost. Then I pulled the chase decision out of the MonoBehaviour into a testable policy object and wrote behavioural tests that simulate a taxi at top speed against the real service rate.

Reinstating the old throttle makes the regression test fail with a concrete number:

Chaser aim point drifted 3.88 m behind the taxi, budget 2.04 m.

Restoring the fix returns the suite to 37 passing. The test proves the fix rather than asserting it.

Skills demonstrated

  • Spatial data structures — a uniform hash grid with a packed cell key and reusable buckets so a per-frame rebuild doesn't allocate.
  • Scheduling and amortization — bounding worst-case frame cost by budget rather than population.
  • Level-of-detail design — scaling work to perceptibility, using squared distances throughout.
  • Benchmarking honestly — asserting equivalence before reporting timing, so a faster-but-wrong structure can't look like a win.
  • Testability through decoupling — separating pure logic from engine types so it can be tested fast and directly.

Course outcomes

  • Outcome 3 — design and evaluate computing solutions, managing trade-offs: the clearest case in this portfolio. Replacing an O(n) scan with a bucketed query, O(n) per-frame work with a bounded O(budget), and unbounded rejection sampling with an O(1) draw — each with its price named. The scheduler trades latency for bounded cost. The grid trades memory and a rebuild for fast queries. If these were bullets instead of zombies, most of these decisions would be wrong.
  • Outcome 4 — well-founded techniques: 37 EditMode tests, including one that cross-checks the grid against brute force on pseudo-random data, because a fast structure returning wrong answers is worse than the slow one it replaced.

Verification

Unity 6000.3.3f1, Unity Test Framework: 37 EditMode tests passing, 0 failures, 0 compile errors.

Coverage spans the grid's correctness against a brute-force cross-check, the scheduler's fairness over a full pass, the level-of-detail band edges, and the chase behaviour against a simulated taxi at top speed.

Zombie Taxi is an unreleased commercial project, so only the gameplay scripts are published — the Unity project itself stays private. The three data structures are plain C# with no engine dependencies, which is both why they're testable in isolation and why they're readable here without the surrounding project.
