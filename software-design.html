Enhancement One · Software Design and Engineering

FrogBlog Backend

An Express 5 and TypeScript API where every route handler did authentication, parsing, database access and the response all at once — restructured into layers with protection enforced by construction.

Browse original code Browse enhanced code Narrative (DOCX)

The artifact

FrogBlog is a full stack blog application I built with my classmates Melody and Julian for CS-465 in late 2025. It's an Express 5 and TypeScript API over MongoDB, with Better Auth handling sessions and a React frontend. Users can register, log in, write posts, and browse a feed.

For the original project I handled the frontend. The backend was mostly my teammates' work, written the way most class projects get written: fast, and to get the demo working for the showcase. For this enhancement I took over the backend, which was the part of the stack I had the least hands-on experience with.

What was wrong

Nothing was crashing. The problems were structural, which is a more interesting thing to fix.

FindingWhy it mattered
Duplicated session checksauth.api.getSession plus a 401 was copy-pasted into two files, written two different ways. Nothing stopped the next route from omitting it entirely.
No error handlingNo Express error middleware anywhere, and no try/catch around any database or auth call.
No input validationA malformed ID went straight to new ObjectId(), which throws — with nothing to catch it.
Hardcoded configurationCORS origin hardcoded; the frontend had http://localhost:3000 typed into five fetch calls despite an environment variable already existing for it.
Dead scaffoldingA posts/ folder with two empty files and an interface that didn't match the real data.

Authentication: from copy-paste to declaration

The clearest single change. The check moved out of the handlers and became something a route opts into.

Before — repeated in every protected handler
async handle(request, response, next) {
    const session = await auth.api.getSession({
        headers: fromNodeHeaders(request.headers)
    })
    if (session == null) {
        response.status(401).json({})
        return;
    }
    const user = session.user

    // ...actual work finally starts here
}
After — protection is declared
export class GetProfileEndpoint extends Endpoint {
    get_type() { return RequestType.GET; }
    get_endpoint() { return "/profile"; }

    override get_middlewares() { return [requireAuth]; }

    async handle(_request, response) {
        const userId = new ObjectId(currentUser(response).id);
        // ...work, with the user guaranteed
    }
}

Two variants exist: requireAuth rejects anonymous requests with a 401, and optionalAuth lets them through but attaches the user when present, which is what lets the public feed show whether you reacted to each post.

Errors: one handler instead of none

Before — unguarded
var author = request.query.author

if (author) {
    // Throws on any malformed value.
    // Nothing catches it.
    query.author = new ObjectId(author)
}
After — validated, then handled
const query = validate(listPostsQuerySchema, request.query);

// Invalid input never reaches ObjectId. The schema
// rejects it and the error middleware turns the
// failure into a 400 naming the offending field.

Handlers now simply throw notFound(), forbidden() or badRequest(). Express 5 routes rejected promises to the error middleware automatically, so none of them need try/catch. The handler maps everything — my own errors, Better Auth errors, MongoDB duplicate keys, and genuinely unexpected exceptions — into one consistent JSON shape.

Skills demonstrated

  • Middleware design — extending an existing routing abstraction with a middleware hook rather than replacing it, so teammates' code kept working.
  • Separation of concerns — a layered architecture where each kind of logic has an obvious home.
  • Defensive programming — validation at the boundary and a single place where failures become responses.
  • Configuration management — environment-driven settings with a documented .env.example.
  • Authorization — ownership checks so a logged-in user can only modify their own content.

Course outcomes

  • Outcome 4 — well-founded techniques and tools: the middleware pattern, a validation library, layered architecture and environment-driven config are the standard ways of solving these problems in the Express ecosystem, used as intended rather than reinvented.
  • Outcome 5 — security mindset: input is validated at the boundary, authentication is enforced by construction instead of by remembering, and modifying a post verifies ownership and returns 403 otherwise.
  • Outcome 2 — professional communication: a rewritten README documenting the full API and the replica-set setup requirement, written so someone else can actually run the project.

Verification

TypeScript typecheck clean under strict mode, including exactOptionalPropertyTypes.

8 unit tests on the pure logic, and 23 integration tests added later against a real MongoDB that exercise the auth middleware, validation and ownership paths end to end.

The integration tests came directly from instructor feedback on this milestone, which asked me to keep developing automated tests to verify the architectural and security improvements. They're documented on the databases page, since that's where they were built.
