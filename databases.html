Enhancement Three · Databases

FrogBlog — MongoDB Data Model

A schema that quietly allowed things it shouldn't have: comments that weren't comments, like counts nobody owned, and no indexes at all.

Browse the models Browse the integration tests Narrative (DOCX)

The artifact

The same FrogBlog project as the software design enhancement, but a different part of it. That one was about how the code is organized. This one is about how the data is shaped and what the database guarantees on its own.

Going back into it meant learning the data layer of a project I had only ever consumed through fetch calls.

What the original schema allowed

FindingConsequence
Comments weren't an entity — a comment was a post with a parent fieldComments leaked into the main feed as if they were posts. Every post query had to know the trick. Nothing stopped a reply from pointing at a comment on a different post.
likes and dislikes were bare numbersNo record of who reacted, so nothing prevented the same user liking a post fifty times, and "have I already liked this?" was unanswerable. No endpoint even incremented them.
No indexesEvery query a full collection scan, including the author filter the profile page runs on every visit.
No validationA document's shape was whatever the handler happened to write that day.
No referential integrityMongoDB won't enforce it for you, and nothing in the application was doing it instead.

Indexes

post      { author: 1, _id: -1 }        author_recent
comment   { postId: 1, createdAt: 1 }   post_thread
reaction  { userId: 1, postId: 1 }      one_per_user_post   UNIQUE
reaction  { postId: 1, type: 1 }        post_counts

one_per_user_post is doing more than making a query fast. Being unique, it is what makes a second reaction from the same user impossible. The application checks too, but the index is the guarantee.

Counters became records

Before — a number anyone could increment
var obj = {
    _id: new ObjectId(),
    author: new ObjectId(user.id),
    title,
    content,
    upload_date: new Date(),
    likes: 0,
    dislikes: 0
}
After — one row per user per post
await collections.reactions().updateOne(
    { userId, postId },
    { $set: { type },
      $setOnInsert: { _id: new ObjectId(),
                      userId, postId,
                      createdAt: new Date() } },
    { upsert: true },
);

Counts are now derived from that collection with a $group aggregation rather than stored as a mutable number, which means the counts and the reactions can't drift apart. The upsert plus the unique index makes setting a reaction idempotent: repeating a like is a no-op, and switching like to dislike updates the same row.

Deletion is atomic

MongoDB has no cascading foreign keys, so deleting a post removes its comments and reactions explicitly — inside a transaction, so either all three happen or none do. This is what required running MongoDB as a replica set, since transactions aren't available on a standalone instance.

const session = client.startSession();
try {
    await session.withTransaction(async () => {
        await collections.comments().deleteMany({ postId: id }, { session });
        await collections.reactions().deleteMany({ postId: id }, { session });
        await collections.posts().deleteOne({ _id: id }, { session });
    });
} finally {
    await session.endSession();
}

Validation, moved into the database

The piece I added specifically for this enhancement, and the decision I'd defend hardest.

I already had Zod validating input at the API boundary from the software design enhancement, and I spent real time deciding whether that was enough before concluding it wasn't. Zod only protects writes that come through the API. My own migration script doesn't go through it. Neither does a console session, or a service someone writes next year.

Every collection except user now carries a $jsonSchema validator specifying required fields, types, string lengths, the allowed reaction values, and additionalProperties: false so a write can't smuggle in a field the model doesn't describe. user is left out on purpose: Better Auth owns that shape and may change it between versions, and pinning a schema to it would break logins on an upgrade.

Mongoose vs. the native driver. I asked about this in two separate journals. Better Auth's adapter uses the native MongoDB driver, so adding Mongoose would mean two data-access layers in one small app. Working through it is what led me here, and I now think this is the better answer: Mongoose validates in the application process; $jsonSchema validates in the database. The constraint ends up closer to the data instead of further from it.

I used validationLevel: "moderate" rather than strict, so pre-existing non-conforming documents stay writable and the migration script is the path to bring them forward. Less satisfying than strict, and the right call with real data.

Proving the guarantees hold

My existing tests covered pure helper functions — pagination maths, comment-tree assembly. Nothing touched the database, which is a real gap when every claim here is about what MongoDB guarantees.

So: 23 integration tests against a real MongoDB, covering the things that only exist at the database level.

What's testedWhy it needs a real database
A user cannot react twice to the same postOnly the unique index can prove this, and only by rejecting the write
Different users may each react; one user may react to different postsConfirms the index constrains the right thing and nothing more
A post with no content, a wrongly typed date, or an unexpected field is rejectedThe validator lives in MongoDB, not in application code
Deleting a post removes its comments and reactions, and not another post'sTransaction behaviour across three collections
A failed authorization check deletes nothing at allNo partial writes on the unhappy path
Pagination walks a twelve-post feed in pages of five, each post exactly once, newest firstCursor ordering guarantees over real documents
Author names degrade to a placeholder when the user is deletedMissing references shouldn't break the feed

The suite reads its database name from .env.test and refuses to start unless that name ends in _test, because it deletes documents and drops the database when it finishes.

Skills demonstrated

  • Normalization — splitting a conflated collection into entities that model what they actually are.
  • Indexing strategy — indexes chosen from real query patterns, including a unique compound index used as a constraint rather than an optimization.
  • Transactions and referential integrity — cascading deletes made atomic, in a database that won't do it for you.
  • Aggregation — deriving counts rather than storing them, so they cannot drift.
  • Schema enforcement — JSON Schema validators at the collection level, with a deliberate validation level.
  • Migration — an idempotent script that brings legacy documents to the new shape.
  • Integration testing — tests against a real database, with a guard so they can't touch development data.

Course outcomes

  • Outcome 4 — well-founded techniques and tools: the strongest case in this portfolio. Normalization, indexing, referential integrity, transactions, schema enforcement and a migration path, each used for a stated reason rather than because it was on a list.
  • Outcome 5 — security mindset: most of what I did here is a constraint that holds whether or not the application behaves. A unique index means stuffing the like count isn't a matter of the client being polite. additionalProperties: false means a request body can't inject a field the model never intended, which is the shape of a mass assignment vulnerability. Validating at the database rather than only at the boundary is defense in depth — it assumes the layer above will eventually be wrong or bypassed.
  • Outcome 3 — algorithmic principles: a smaller contribution, through the indexing and aggregation decisions.
